# Daemon Split Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** One `postbode run` daemon owns sync, rules, notifications and every IMAP command. The GUI, CLI and MCP become clients over a 0600 Unix socket that speaks JSON lines.

**Architecture:**
- A request id travels with every command from the client, through the daemon, to the account thread. The completion events carry it back, and the daemon turns them into replies while still broadcasting them to subscribers.
- `daemon::run` wraps the existing `Engine` with a socket server on std threads.
- `daemon::Client` is the only way a front end reaches IMAP. It auto-starts `postbode run --idle-exit 60` when no daemon answers.
- Reads stay direct SQLite.

**Tech Stack:**
- Rust 1.99, edition 2024.
- std `UnixListener`/`UnixStream` with threads; no new dependency.
- serde and serde_json for the wire.
- The existing `Engine`, `sync` and `RecordingOps` for tests; egui_kittest for the GUI.

**Spec:** `docs/superpowers/specs/2026-10-07-postbode-daemon-design.md`. The core, GUI and MCP specs it builds on still bind everything else.

## Global Constraints

**Definition of done**
- These must pass: `cargo fmt --check`, `cargo clippy --all-targets --all-features -- -D warnings`, `cargo test --all-features`, `cargo check --no-default-features --all-targets`, `cargo machete`, `cargo audit`. The ttf-parser RUSTSEC-2026-0192 warning is allowed.
- No new dependency.
- Platforms: macOS and Linux only (Unix sockets). Report "ran on macOS"; CI covers Linux.

**Files and modes**
- Socket `<state>/daemon.sock`, mode 0600.
- Lock `<state>/daemon.lock`, which holds the pid.
- Log `<state>/daemon.log`, truncated at daemon start when it exceeds 1 MB (1 048 576 bytes).

**Lifecycle**
- Auto-start spawns `<current_exe> run --idle-exit 60`.
- It is detached into a new process group with stdin from `/dev/null`, and stdout and stderr appended to the log.
- The client retries the connect for up to 5 s.
- Idle exit: 60 s with no connected client, and only with `--idle-exit`. Plain `postbode run` never idles out.
- Config poll: every 2 s, on the modification time of `config.toml`.

**Protocol**
- `protocol` is `1`; `version` is `env!("CARGO_PKG_VERSION")`. Any mismatch in either makes the client stop the daemon and start its own binary.
- Client reply timeout: 120 s. The timeout text is `no reply from the daemon within 120 s; the command may still run, see \`postbode log\``.
- Every message with an `id` gets exactly one reply. Events go only to clients that subscribed.

**Error texts**
- Unknown account: `no account named '<name>'`.
- Offline account: `<account> is offline (<reason>); retrying at <HH:MM>`. The time is local, from `chrono`.
- Second daemon: `already running (pid <N>)`.
- Daemon gone mid-request: `the daemon stopped; see <state>/daemon.log`.

**Attribution**
- `Apply.by` is logged as the action's rule name.
- CLI uses `cli`, GUI uses `gui`, MCP uses `mcp:<client>` (or `mcp` with no client name).

**Rules for agents**
- Stdout carries only the MCP protocol while `postbode mcp` serves. The daemon and client libraries never `println!`. Only `cli/` and the foreground `run` report print.
- Comments: one line, only for a non-obvious why, no history references. Conventional commits, no attribution lines.
- Never run `kache init`, never push, never run `launchctl` or `systemctl` in tests, never run `postbode service install` without `--dry-run`.

## Review Focus

1. **Client timeout while the command still runs later.** A command queued just before the account went offline, or behind a long first-sync chunk, replies after the 120 s timeout. The user must be told it may still run, not that it failed. Task 4 pins the exact timeout text with a short injected timeout.
2. **Daemon killed with -9.** It leaves a stale socket file, and the OS releases the lock. The next auto-start must bind and serve, not fail with "address in use". Task 3 adds a stale-socket test.
3. **Two clients auto-starting at once.** Exactly one daemon must win, and both must connect to it. Task 4 starts two `connect_or_start` threads on one temp home and asserts the same pid.
4. **Old daemon after an upgrade.** A client of a newer version must stop it and start its own binary rather than talk an old protocol. Task 4 tests this with an injected version.
5. **Daemon stopped while the window is open.** The GUI must show "background sync stopped — reconnecting" and recover when the daemon is back, not freeze or crash. Task 7 adds a kittest.

## Rulings made while planning

- **Wire shape.** Messages are externally tagged serde enums: `{"hello": {...}}`, `{"command": {"id": 8, "account": "work", "command": {...}}}`, `{"reply": {"id": 8, "outcome": {"ok": {...}}}}`, `{"event": {...}}`. The spec's §5 example lines are indicative; Task 3 updates them to the real shapes. A flattened top level would need hand-written serde for no gain.
- **Account locks and `StartState::Locked` are removed (Task 8).** The daemon lock already guarantees one engine per machine. `lock_account` and `Locked` exist only for several processes.
- **Notifications in the daemon** follow each account's `notify` flag, as the GUI does today.
- **A fire-and-forget command rejected at once** (GUI) arrives on the client's event channel as `Event::CommandFailed`. Successful replies to fire-and-forget commands are dropped, because the broadcast event already reached the subscriber.
- **`Paths` gains `home: Option<PathBuf>`.** `under` sets it and `discover` leaves it `None`. Auto-start passes `POSTBODE_HOME` to the child when it is set, so the daemon a test home starts uses that home.
- **Engine gets per-account start and stop** (`apply_config`), so a config change restarts only changed accounts, as §4 of the spec asks.
- **Ids for internal broadcasts.** `Event`s produced without a request (sync passes, rules) carry `request: 0` or `requests: []`. Ids start at 1.

```rust
impl Event {
    /// The requests this event completes, so the daemon can reply to whoever sent them.
    pub fn request_ids(&self) -> Vec<RequestId> {
        match self {
            Event::ActionDone { request, .. }
            | Event::BodiesFetched { request, .. }
            | Event::BodyReady { request, .. }
            | Event::CommandFailed { request, .. }
            | Event::Restored { request, .. }
            | Event::RuleApplied { request, .. } => vec![*request],
            Event::Synced { requests, .. } => requests.clone(),
            Event::Activity { .. } | Event::Error { .. } | Event::NewMail { .. } => Vec::new(),
        }
    }
}
```

`src/daemon/mod.rs`, in this order of responsibilities:

1. **Startup.** The state directory is the access boundary: other users must not be able to reach the socket, even in the moment between `bind` (which creates it with the umask's mode) and `set_permissions`.
   - `paths::create_private_dir(&paths.state_dir)`, which also resets an existing directory to 0700. Call it before `bind`.
   - Truncate `daemon_log()` if it is over 1 MB.
   - Open `daemon_lock()` and `try_lock()`. On `WouldBlock`, read the pid and bail `already running (pid {pid})`. Otherwise write our pid.
   - Remove a leftover `daemon_socket()`, then `UnixListener::bind`. On `ErrorKind::InvalidInput`, bail `socket path too long: {path}`.
   - Set the socket's permissions to 0o600.
   - Load the config. A config that fails to load is an error at start.
   - `Engine::start_with(&config, paths, options.connect.clone())`.
2. **Shared state:** `Arc<Mutex<Hub>>`.
   - `clients: HashMap<ClientId, ClientConn { out: Sender<String>, subscribed: bool }>`.
   - `pending: HashMap<RequestId, (ClientId, u64)>` and `next_request: RequestId`.
   - `activity: HashMap<String, Activity>`.
   - `last_client_left: Instant`, `shutdown: bool` and `started: Instant`.
   - Each client has a writer thread draining its `Receiver<String>` into its stream, so a slow client never blocks the hub.
3. **Event thread.** For each `Event` from the engine:
   - Record `Activity` per account.
   - When `options.report`, print the line `print_event` prints today: move `print_event` from `cli/mod.rs` into `daemon/mod.rs` as `fn report(event: &Event)`.
   - When `options.notify` and the account's `notify` is set, call `notify::new_mail` for `NewMail`.
   - For each id in `event.request_ids()`, remove `pending[id]` and send that client `Reply { id: client_id, outcome: Ok(Payload::Event(event.clone())) }`. For `CommandFailed`, send `Outcome::Error(message)` instead.
   - Then send `DaemonMessage::Event(event)` to every subscribed client.
4. **Accept loop.** Set the listener non-blocking and poll every 200 ms. Each round:
   - Check `hub.shutdown`, the idle exit (`clients.is_empty() && last_client_left.elapsed() >= idle`), and the config modification time every 2 s, which runs `Config::load` then `engine.apply_config`. An error is logged and the running accounts kept.
   - A new connection gets a reader thread.
5. **Reader thread per client.**
   - The first line must be `Hello`. Reply `Hello { protocol: PROTOCOL, version: VERSION, pid }`.
   - Then for each line:
     - `Subscribe` → mark subscribed and reply `Ok(Done)`.
     - `Status` → reply `Ok(Status(..))` with each account's `StartState` and last activity.
     - `Shutdown` → reply `Ok(Done)` and set `hub.shutdown`.
     - `Command`, checked in this order:
       - an unknown account replies `Error("no account named '{account}'")`;
       - a `Failed` state replies with its reason;
       - a last activity of `Offline { reason, retry_at }` replies `Error("{account} is offline ({reason}); retrying at {HH:MM}")`, formatted with `chrono::Local`;
       - otherwise assign a request id, record `pending`, and `engine.send(&account, request, command)`.
     - A line that does not parse replies `Error("bad message: {e}")` when an `"id"` number can be read from it as JSON, and otherwise closes the connection.
   - On EOF, remove the client and its pending entries, and set `last_client_left` when it was the last.
6. **Exit.** Drop the engine, which stops and joins the threads. Remove the socket file, release the lock (drop the `File`), and return `Ok(())`.

The `Engine` is owned by the accept-loop thread. Readers reach it through `Arc<Mutex<Engine>>`, or through a `Sender<(String, RequestId, Command)>` drained by the loop. Pick the latter if `Engine` is not `Send`, and say which in the report.
